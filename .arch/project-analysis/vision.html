Internal Vision / Static Briefing

A project analysis system that tells us what to improve next

Existing tools can describe code. They do not tell this project what matters now. Our layer combines semantic code facts, dependency graphs, tests, and repository history into a ranked work queue for maintainers.

Inputs

LSP, dependency graph, tests, git, filesystem

Engine

Normalized snapshots and analyzers

Outputs

Hotspots, orphan files, test gaps, compare reports

Value

Clear next actions instead of raw tool noise

The core problem

Tooling today: facts are scattered across editors, CLIs, test logs, and git history.
Team pain: it is hard to see what is risky, stale, central, weakly tested, or safe to remove.
Decision gap: raw diagnostics do not become a prioritized maintenance roadmap.

How the system works

We do not rebuild language servers or graph tools. We reuse them, then add a thin project-specific analysis layer on top.

Collect facts
Normalize snapshot
Run analyzers
Show ranked actions

What it orchestrates

Collectors

LSP, dependency graph, file inventory, tests, git churn.

Snapshot

One shared JSON model for routes, components, symbols, diagnostics, and metrics.

Analyzers

Hotspots, orphan files, route graph, test gaps, duplication, trends.

Surfaces

API, dashboard, compare view, markdown reports, mermaid graphs.

Why not just use existing tools directly?

  • LSP tells us symbols, references, and diagnostics.
  • Dependency tools tell us graph shape and cycles.
  • Tests tell us pass or fail.
  • None of them ranks repository work for this product.

What our layer adds

  • Repository-specific heuristics for routes, content, and shared UI.
  • Consistent snapshot storage over time.
  • Priority scoring across risk, impact, and effort.
  • One place to compare architectural health between runs.

What it can say

  • The homepage is a hotspot with growing dependency fan-out.
  • These preview pages are unreferenced and removable.
  • This public route has no verification signal.
  • This data file is becoming a central coupling point.

Signals the system should surface first

Risk

Hotspots

Public entrypoints, high fan-out, high churn, low confidence.

Waste

Orphan Files

Unused components, assets, preview pages, or content without reach.

Coverage

Test Gaps

Important user-facing routes and central components with weak verification.

Trend

Compare

Whether architecture improves or degrades between snapshots.

What success looks like

For maintainers

Faster triage, clearer refactor targets, fewer blind spots.

For product owners

Evidence-backed priorities instead of intuition-only cleanup work.

For future AI agents

A stable fact layer for explaining risk, planning work, and comparing change impact.

Before

  • Many tools, many outputs, no shared memory.
  • Manual guessing about what is central or stale.
  • No repository health trend.
  • Cleanup work competes poorly with feature work.

After

  • One snapshot model for code, content, tests, and history.
  • Ranked findings with reasons and suggested actions.
  • Time-based comparisons across branches or commits.
  • Internal dashboard for architecture review.

Execution path

  • Phase 1: snapshot generator
  • Phase 2: hotspot and orphan analyzers
  • Phase 3: compare and trend reporting
  • Phase 4: dashboard inside the app

Technical value

  • Reusable facts from proven external tools
  • Small custom layer instead of rebuilding LSP or graph engines
  • Stable schema for future automation

Operational value

  • Better prioritization of maintenance work
  • Higher confidence for refactors
  • Lower risk of dead code and hidden regressions

Strategic value

  • A project that can explain itself
  • Shared visibility for humans and agents
  • A path from diagnostics to architecture decisions
